# Вход по приглашению и административный экран

## Что означает offline-first при обязательном входе

Первая активация устройства требует сети и действующего кода. Затем приложение открывает уже созданное локальное хранилище без обращения к серверу. Локальные операции, настройки, бюджеты, карты, иконки, графики и уведомления доступны при отсутствии сети и при истечении сетевого access token. Отсутствие сети не является поводом очистить БД или разлогинить локального пользователя.

После первой загрузки и активации веб кеширует app shell и сохраняет данные в IndexedDB. Нельзя обещать первый в жизни запуск веб-сайта без интернета. Приватный режим/очистка browser storage могут уничтожить локальные данные; об этом нужно сообщать по фактически обнаруженной проблеме.

## Типы кодов

| Тип | Для чего | Привязка |
|---|---|---|
| NEW_USER | Первичная активация нового пользователя | Создаёт новый user и первое устройство |
| ADD_DEVICE | Вход на второй телефон/веб или восстановление доступа | Заранее привязан администратором к существующему userId |

Оба типа выпускаются только admin. Код одноразовый, случайный минимум 128 бит; представление — 26 символов Base32, группировка для удобного ввода, paste/QR. Это bearer secret: кто имеет код, может активировать устройство. Он показывается администратору один раз; сервер хранит HMAC/хеш кода, дату истечения, purpose, targetUserId, creator, state. Не использовать короткий шестизначный код как долгоживущий секрет.

Срок по умолчанию 72 часа, настраивается при выпуске в пределах серверного лимита. Для ADD_DEVICE рекомендуется короткий срок, например 30 минут. Состояния: active/expired/redeemed/revoked. Выпуск admin-приглашений через обычный экран запрещён: публично создаются только USER. Роль ADMIN назначается отдельной серверной командой bootstrap/оператором, с журналированием.

## Активация и сессии

`POST /api/v1/activation/redeem`: code, deviceName, platform, clientRequestId. По коду определяется новый или существующий пользователь. Клиент не выбирает роль или userId. Для веба ответ устанавливает Secure HttpOnly SameSite cookie; Android получает короткий access token и rotating refresh token. Сервер хранит хеш refresh token и состояние устройства. Транспорт HTTPS.

Потребление приглашения и создание user/device/session выполняются одной серверной транзакцией. Два конкурентных запроса с одним кодом дают максимум одну активацию. Ошибка ответа после commit не должна оставлять «сгоревший код без возможности получить сессию»: для первоначального redeem клиент создаёт ephemeral request secret, сервер кратковременно хранит зашифрованный ответ, привязанный к clientRequestId и его хешу. Повтор того же запроса с тем же secret возвращает тот же результат, другой запрос — CODE_ALREADY_USED. Secret не помещать в URL/logs, удалить после подтверждения сессии. Допускается иной стандартный проверенный протокол idempotent activation, но его надо документировать и проверить на потерю ответа.

Refresh rotation: токен одноразовый, повтор не считается новой авторизацией. Потеря ответа на refresh решается коротким ограниченным idempotency окном, а не бесконечным сроком токена. По окончании offline-периода, если refresh уже недействителен, пользователь вводит новый ADD_DEVICE код к тому же userId. Перед сменой локального namespace проверить returned userId; чужому аккаунту не прикреплять существующие данные.

Паролей, публичной регистрации, Google login, email OTP и входа «просто по userId» нет. Отправка приглашений через email/мессенджеры автоматически не требуется; admin копирует код или QR самостоятельно.

## Административный экран

Экран «Администрирование» появляется только у активного admin. UI скрытие не заменяет server-side RBAC. Первичное создание admin — CLI-команда на сервере с выводом одноразового bootstrap-кода, доступная только оператору с серверным доступом; общий публичный `/setup` и стандартный admin password отсутствуют.

Вкладки:

1. Приглашения: создать NEW_USER, создать ADD_DEVICE с выбором пользователя, срок, копирование, активные/погашенные/отозванные, отзыв.
2. Пользователи: ID, отображаемое имя, статус, дата создания, список устройств. Финансовые операции пользователей администратору не показываются.
3. Устройства: дата последней связи, платформа, отзыв конкретной сессии/всех сессий.
4. Журнал: кто/когда создал/погасил/отозвал код или устройство; без raw codes и финансовых payload.

Управление доступом требует online. В offline можно показать кеш последнего списка с датой обновления, но нельзя сгенерировать действующий серверный код локально или показывать локальное действие как уже выполненное. Такие команды не попадают в общую финансовую outbox; UI объясняет, что требуется соединение. Пользовательские данные при этом остаются полностью работоспособными.

## Отзыв и ограничения

Отзыв активного неиспользованного code предотвращает активацию. Отзыв session/device прекращает серверный доступ при следующем запросе. Устройство без сети технически продолжит видеть ранее сохранённые локальные данные и вводить новые; удалённое мгновенное стирание не заявляется. После обнаружения отзыва sync блокируется, outbox сохраняется; данные можно экспортировать локально. Возобновление — новый ADD_DEVICE код от admin, без потери очереди того же userId.

Админ не получает права чтения чужих расходов. Для поддержки достаточно диагностических кодов и счётчиков; просмотр пользовательских финансов потребовал бы отдельного явно согласованного продуктового решения.

## Проверки

Погашение/истечение/отзыв кода; race двух клиентов; lost response/retry; brute force/rate limits; отсутствие enumeration по ошибкам; запрещённый admin endpoint для USER; forged role/userId; отсутствие кодов в URL/logs; безопасный QR; первое устройство и ADD_DEVICE на тот же аккаунт; возврат после длительного offline; expired refresh без удаления БД; revoke не удаляет outbox; новый код другого userId не объединяет чужие данные.

## Доступ и расшифровка — разные этапы

Сервер хранит синхронизированные данные в E2EE виде. После NEW_USER активации создаётся vault и recovery key. После ADD_DEVICE активации запрашивается существующий recovery key для локального раскрытия vault. Admin-приглашение не является ключом расшифровки. Обязательный механизм и сценарий потери ключа: `ENCRYPTION.md`. Пароль для входа не добавляется.
