# Шифрование и ключи

## Принятое проектное решение

Все долговременные пользовательские данные имеют локальную копию и синхронизированную серверную копию. Для сервера предлагается E2EE: финансовое содержимое зашифровывается на клиенте до отправки. HTTPS и шифрование диска/backup сервера используются дополнительно, но не заменяют E2EE. Это проектная рекомендация, а не заявление о готовом или прошедшем криптоаудит приложении.

| Данные | Серверная копия |
|---|---|
| Операции, суммы, продавцы, заметки, категории, теги | Зашифрованные records |
| Банки, счета, карты, last4, пользовательские названия | Зашифрованные records |
| Бюджеты дня/недели/месяца, обязательства, цели, фильтры | Зашифрованные records |
| Пользовательские иконки | Зашифрованные blobs; тип изображения проверяется клиентом до шифрования |
| Синхронизируемые правила/профили уведомлений | Зашифрованные records; системный grant остаётся устройству |
| Review candidates, решения и связи импорта | Зашифрованные records без лишнего сырого текста |
| Offline outbox | Локальная очередь; на сервере применённые зашифрованные команды/receipt |
| Сырые notification payload | Временный inbox/диагностика локально; не долговременная пользовательская история |
| user/device IDs, role, код/срок/статус приглашения, revision/cursor, размер и время blob | Служебные метаданные в открытом для сервера виде |

Сервер видит техническую активность и размеры. Название entityType тоже может раскрывать тип записи; для повышенной приватности можно использовать общий RECORD, но начальный протокол явно документирует эту утечку метаданных. Админ видит пользователей/устройства, не расшифрованные расходы. Активно скомпрометированный веб-сервер способен подменить исполняемый web-клиент, поэтому E2EE браузера не считается защитой от вредоносной версии самого приложения или XSS.

## Иерархия ключей

При первичной настройке новый активированный клиент генерирует случайный 256-битный VaultKey через криптографический генератор платформы. Пароль от аккаунта не нужен. Сервер никогда не получает этот ключ в открытом виде.

Для records/assets используется AES-256-GCM с 128-битным authentication tag и корректным 96-битным nonce. Конкретная библиотека — cryptography-kotlin с платформенными провайдерами JCA/WebCrypto либо минимальные platform adapters поверх стандартных APIs. На первом этапе обязательна проверка Android ↔ Wasm совместимости.

Domain-separated subkeys выводятся стандартным HKDF-SHA256 с зафиксированным salt и length-prefixed info, включающим vaultId, entityId/assetId, keyVersion и purpose. Формат info и AAD задаётся бинарной/канонической сериализацией, а не конкатенацией строк через неоднозначный разделитель. Не писать свою реализацию AES/HKDF или Base32 random generator.

Nonce должен быть уникален на ключ. Использовать библиотечный CSPRNG, новый nonce на каждую новую encryption operation, тесты на отсутствие повторного применения nonce при редактировании и перезапусках. Повтор отправки неизменной команды передаёт прежний ciphertext/nonce, а не шифрует заново. Производные ключи по entity/версии ограничивают область возможной коллизии. Зафиксировать лимиты использования и ротацию до массового применения; не считать проверку случайной выборки доказательством уникальности во всех будущих вызовах.

AAD связывает userId/vaultId, entityId, entityType, schemaVersion, keyVersion. Перенос ciphertext к другому entity/user должен проваливать authentication. ServerRevision назначается после записи и не используется в AAD исходного шифрования. Для pull проверяется монотонность серверной revision; защита от активного server rollback за пределами обычной модели утечки БД требует отдельного протокола и не обещается.

### Формат T03 (v1)

Каждое поле канонической последовательности кодируется как 4 байта длины (big-endian), затем UTF-8 без нормализации. Пустые поля и некорректный UTF-16 отклоняются. Версии схемы и ключа — положительные Int, записанные десятичными ASCII-цифрами без ведущих нулей. Порядок полей фиксирован:

| Назначение | Поля по порядку |
|---|---|
| HKDF info | `ladno/payload-key/v1`, vaultId, entityId, keyVersion, purpose |
| Payload AAD | `ladno/payload-aad/v1`, userId, vaultId, entityId, entityType, schemaVersion, keyVersion, purpose |
| Local wrap AAD | `ladno/local-wrap/v1`, userId, vaultId, keyVersion |

HKDF-SHA256 использует salt из UTF-8 строки `ladno/hkdf-sha256/v1` и выдаёт 32 байта. Для purpose предусмотрены значения `record` и `asset`. Envelope содержит `01 || nonce[12] || ciphertext || tag[16]`. Для локального wrapping длина envelope ровно 61 байт. Контекст передаётся отдельно и сверяется через GCM; неизвестная версия envelope отклоняется. При интеграции sync отдельные поля JSON кодируются по SYNC_API.

Новые операции получают nonce от CSPRNG. Для локального wrapping Android выдаёт nonce через Keystore, веб — через WebCrypto. Повтор отправки должен читать готовый envelope из outbox. Перед массовой синхронизацией нужно реализовать учёт лимита и ротацию. Верхняя граница для случайных 96-битных nonce — не более 2³² шифрований на ключ суммарно по всем устройствам, включая локальные ключи wrapping. [NIST SP 800-38D, §8.3](https://csrc.nist.gov/pubs/sp/800/38/d/final).

Решение T03: payload использует провайдеры cryptography-kotlin для общих алгоритмов. Локальные wrapping keys остаются внутри Android Keystore или WebCrypto; кроссплатформенное представление применяется только к зашифрованным байтам. Клиент передаёт стабильный локальный alias/key ID. При отсутствии ключа unwrap завершается ошибкой, чтобы клиент мог предложить recovery. Хранилище самого wrapped envelope подключается на этапе интеграции vault.

## Ключ восстановления и новые устройства

На первом устройстве также создаётся случайный 256-битный RecoverySecret, отображаемый в виде recovery-файла/QR/группированного текста. Он не является кодом приглашения и не отправляется на сервер. Из него HKDF выводит RecoveryWrapKey; VaultKey шифруется этим ключом со своим nonce и AAD. На сервер отправляется только recovery envelope и несекретные параметры.

Инициализация vault выполняется compare-and-set: только один клиент может создать начальный recovery envelope для нового vault. Если другой клиент уже создал vault, новый клиент переходит к восстановлению, а не генерирует второй несовместимый ключ.

Пользователь сохраняет recovery-файл отдельно и подтверждает сохранение до включения серверной синхронизации зашифрованного vault. Сам RecoverySecret не оставлять в URL, логах, crash report или открытой серверной БД. Он не нужен для каждого запуска устройства.

Подключение второго устройства:

1. Администратор выпускает ADD_DEVICE приглашение, привязанное к тому же userId.
2. Устройство активирует сессию и получает encrypted snapshot и recovery envelope.
3. Пользователь импортирует recovery-файл/ключ. Клиент локально раскрывает VaultKey и проверяет authenticity envelope.
4. Ключ сохраняется защищённо на устройстве, records расшифровываются локально и индексируются для поиска/графиков.

В месячном плане обязательный путь — recovery key. Передача ключа с уже подключённого устройства через защищённое pairing/QR может быть отдельным последующим удобством: не блокировать релиз из-за собственного протокола peer-to-peer. Просто код приглашения не даёт расшифровать старые данные. Если потеряны все устройства и recovery key, администратор может восстановить доступ к аккаунту, но не содержимое vault. Это нужно объяснить до подтверждения настройки.

## Локальное хранение

Android: VaultKey завернуть локальным AES wrapping key из Android Keystore. Wrapping key неэкспортируемый. Listener должен иметь возможность сохранять входящие уведомления без интерактивной биометрии, поэтому режим «каждая операция только после biometric prompt» несовместим с автоматическим сбором. Блокировка UI и шифрование фонового хранилища — разные механизмы. После перезагрузки до первого разблокирования можно буферизовать минимум в доступном защищённом app storage и честно показывать пробелы импорта; не обещать обход device lock.

Web: локальный wrapping key — неэкспортируемый WebCrypto CryptoKey в IndexedDB, если выбранные браузеры поддерживают этот сценарий; совместимость проверяется spike. VaultKey сохраняется завёрнутым. При утрате CryptoKey/браузерного профиля используется RecoverySecret. Неэкспортируемость не защищает от JavaScript, уже выполняющегося в том же origin. Никаких сторонних analytics scripts на страницах приложения; CSP, безопасное отображение пользовательского текста и контролируемый service worker обязательны.

Локальные records/assets и payload outbox также шифровать; для UI/поиска держать расшифрованные необходимые проекции в памяти и перестраивать при запуске. Room/IndexedDB содержат opaque records, sync metadata и минимальные несекретные индексы. Не оставлять суммы/merchant/cards в открытых SQL/IndexedDB индексах, если заявлено шифрование локальных финансов. Начальные 10–50 тыс. records обрабатываются постранично, с прогрессом и фоновым разбором; производительность измеряется.

Временный raw inbox на Android требует отдельного device-protected ключа для фоновой записи; он локальный и ограничен сроком хранения. Если безопасный ключ недоступен, событие не логировать в открытом виде: показать диагностику невозможности импорта. Это ограничение важнее фиктивного обещания 100% захвата.

## Изменение роли backend

Backend хранит ciphertext и проверяет session owner, epoch, metadata schema, длину/размер записи, idempotency и optimistic revision. Он не может валидировать сумму splits, card→account, валюту и баланс бюджета, поскольку не расшифровывает payload. Эти инварианты проверяет общее Kotlin-ядро клиентов перед записью и после расшифровки входящих данных.

Невалидный расшифрованный record помещается в quarantined conflict/error state и не используется для финансовых расчётов. Серверные FK финансовых сущностей не требуются: ссылки находятся внутри ciphertext. Нельзя одновременно обещать zero-knowledge backend и серверную аналитику по открытым merchant/amount. Поиск, аналитика, рекомендации и графики выполняются на клиенте.

Asset endpoint проверяет ciphertext size и права; он не декодирует PNG и не узнаёт sha256 открытой картинки. Клиент проверяет image signature/размер/декодирование перед сохранением и повторно после decrypt. Content hash открытого изображения остаётся внутри зашифрованного manifest, чтобы не раскрывать одинаковые иконки между аккаунтами.

## Ротация, резервирование и границы

У каждого record есть keyVersion и formatVersion. Ротация VaultKey создаёт новую версию, новые записи шифруются новым ключом, старые мигрируют в фоне с прогрессом и сохранением прежних keys до полного подтверждения. Recovery envelope обновляется атомарно через optimistic revision. Ротация не удаляет уже прочитанные данные с отозванного офлайн-устройства; без полной перешифровки старого vault нельзя запретить старому ключу чтение старых ciphertext.

Серверные backups содержат encrypted records, recovery envelopes, revisions и служебную identity БД. Данные пригласительных/сессий защищаются отдельно. Удаление и retention документируются, включая срок жизни backups. Экспорт CSV/JSON по явному действию расшифрованный и помечается соответствующе. Зашифрованный backup содержит версионированный manifest и authenticated ciphertext, восстановление проверяется на втором устройстве.

Минимальные тесты: golden vectors Android/Wasm; wrong key; modified tag; modified AAD; swapped entity/user; corrupted envelope; non-repeat nonce при новой записи; exact retry ciphertext; recovery на новом устройстве; потерянный recovery; offline launch с wrapped key; restart во время key migration; ошибочный payload не попадает в аналитику; отсутствие plaintext финансов в server DB/logs и локальных persisted indices.
