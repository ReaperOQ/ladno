# Уведомления: импорт, ошибки, дубли

## Обязательный поток

`package allowlist → bounded extraction → durable inbox → text filter → parser → dedup/candidate matching → category/account/card resolution → confirmation/review → atomic local commit + outbox`.

Listener и импорт работают без регистрации в сети после первичной активации устройства, без доступного backend и без открытого экрана. Отозванный/истёкший сетевой token не должен ломать локальный listener. ОС всё равно может остановить процесс; пропущенную историю не обещать восстановить. После reconnect обрабатывать активные уведомления через тот же дедупликационный путь.

Состояния inbox: received → filtered / unsupported / redacted / parsed → confirmed / needs_review / ignored. При crash незавершённое received подхватывается повторно. Ошибка одного события не блокирует следующие. Все переходы идемпотентны. Удаление карточки уведомления из шторки не удаляет уже учтённый расход.

| Случай | Действие |
|---|---|
| Пакет не выбран | Не читать extras, не сохранять payload |
| Реклама/OTP/приглашение банка | Игнорировать по фильтрам/профилю; OTP не копировать в диагностику |
| Системная group summary | Пропустить агрегат; индивидуальные сообщения обрабатывать отдельно |
| Title/text/bigText повторяют одно сообщение | Выбрать наиболее полный вариант; не создавать несколько операций |
| В уведомлении несколько явных операций | Парсер либо возвращает несколько кандидатов со стабильными sourceItemId, либо review; не считать только первую без предупреждения |
| Покупка + остаток | Выбрать только сумму с маркером операции; баланс не сохранять |
| Неизвестный формат/сумма | Needs review; не создавать нулевой расход |
| Недоступный или скрытый текст | Reason REDACTED_OR_EMPTY; счётчик диагностики и ручной ввод |
| Входящее зачисление | Income либо refund/transfer по подтверждённой связи; неизвестное направление в review |
| Одинаковые покупки рядом | Сохранить обе, если нет доказательства одной операции; предложить проверку дубликата |
| Перевод между своими счетами | Создать/связать один transfer aggregate; не две расходные операции |
| Только одна сторона перевода | Кандидат требует подтверждения второго счёта; можно оставить income/expense только осознанным решением пользователя |
| Счёт/карта не определены | Pending; пользователь выбирает счёт/карту |
| Две карты с одинаковыми last4 | Учитывать банк/источник и account mapping; неоднозначное — review |
| Источник отключён | Новые события не импортировать; историю не удалять |

## Точная и вероятностная дедупликация

1. **Delivery dedup**: deviceId + packageName + Android notification key + digest нормализованного содержимого + временное окно; сохраняется последнее состояние key. Повторная обработка одного inbox event всегда даёт тот же результат. Старый key с новым содержимым не отбрасывается автоматически.
2. **Operation dedup**: уникальный банковский operationId внутри профиля источника, если он действительно содержится в тексте и проверен. Несколько evidence могут указывать на одну transaction.
3. **Candidate match**: account/card + amount + currency + merchant + близкое время; это предложение пользователю, а не ключ уникальности. Нет гарантии, что банк присылает уникальный ID.
4. **Sync dedup**: commandId и transactionId не меняются при retry. Повтор той же команды не создаёт новую операцию.
5. **CSV match**: тот же принцип — идентификатор строки/операции по файлу; fuzzy match просит подтверждение. Повторная загрузка файла показывает уже импортированные строки.

Если одно уведомление изменило сумму, а пользователь уже правил операцию, исходные поля не перезаписываются молча. Создать review с diff. Обновление pending → settled обрабатывается только по проверенному profile rule. Изменение парсера даёт preview повторного разбора и никогда не удаляет/не заменяет confirmed операции автоматически.

## Формат fixtures

Каждая fixture содержит `fixtureId`, `profileId`, `profileVersion`, `packageName`, `fields`, `capturedAt`, `expectedOutcome`, `expectedCandidates`, `expectedReason`. Значения синтетические. Отдельно размечать synthetic и реальные обезличенные fixtures. До наличия реального примера статус профиля experimental, не supported.

Набор для каждого профиля: debit, income, refund, own transfer, fee, два числа с балансом, NBSP/узкий пробел, comma/dot decimals, отсутствие копеек, отрицательная запись, маска карты, неизвестная карта, совпавшие last4, повторная доставка, изменение карточки, reuse key для новой покупки, group summary, рекламный push, OTP, скрытый текст, truncated text, malformed number, сумма сверх диапазона, чужая валюта.

Тестовый notifier — отдельное debug-only приложение с собственным пакетом и синтетическими уведомлениями. Оно не имитирует package ID банка. Debug allowlist не попадает в release профили. Нельзя подключать обход системной защиты чувствительных уведомлений.

## Durable inbox и приватность

В системном callback не выполнять сеть и долгие расчёты. Сначала минимальный фильтр пакета, затем bounded envelope, затем короткая запись в локальный inbox на IO executor; последующий worker продолжает разбор. Пустой/полный диск и quota errors должны давать видимое состояние ошибки импорта. Нет абсолютной гарантии записи события при kill процесса до завершения durable commit — это ограничение отображается через диагностический статус, а не маскируется.

Сырые данные только локальные. Подтверждённое/отфильтрованное событие после обработки очищает текст; pending хранит минимальный текст до разрешения, максимум 7 дней. Никаких OTP/PAN/полных реквизитов в logs/fixtures/analytics. Если токенизация текста обнаружила дополнительные банковские числа, они не становятся балансом счёта.

## Несколько устройств-сборщиков

По умолчанию для одного источника/набора счетов выбирается одно основное устройство-сборщик; остальные устройства получают операции через sync. Выбор хранится в зашифрованной source configuration, системный grant остаётся локальным. Если пользователь сознательно включает сбор одного банка на двух устройствах, точное межустройственное связывание возможно только при стабильном operationId. При его отсутствии после sync предлагается review возможного дубля; одинаковая сумма/время не являются доказательством. Одновременное offline включение двух сборщиков не позволяет гарантировать отсутствие таких кандидатов.
